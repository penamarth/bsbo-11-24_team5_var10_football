Рамки. Приложение организации мероприятий и продажи билетов Stadium Management and Tickets System.

Уровень. Задача, определенная пользователем.

Основной исполнитель. Менеджер.

Заинтересованные лица и их требования.

- Менеджер. Хочет быстро получать наглядную аналитику по мероприятию: выручку, количество проданных билетов и абонементов, заполняемость стадиона, чтобы оценивать результаты и планировать будущие мероприятия.
- Организатор мероприятия. Хочет видеть итоги прошедшего мероприятия и понимать, насколько прибыльным оно оказалось.
- Компания владелец стадиона. Заинтересована в достоверных данных о выручке и загрузке стадиона для принятия решений.
- Система анализа прибыльности мероприятия. Требует своевременного получения агрегированных данных о продажах билетов и абонементов для расчета прибыльности.

Предусловия. Менеджер идентифицирован и аутентифицирован в системе. В базе данных хранятся сведения о мероприятии и проданных на него билетах и абонементах.

Результаты (Постусловия).

- Показатели мероприятия рассчитаны.
- Отчет по мероприятию сформирован и отображен менеджеру.
- Отчет сохранен в базе данных и доступен для выгрузки.
- Агрегированные данные о продажах и занятых местах переданы в систему анализа прибыльности мероприятия.

Основной успешный сценарий (или основной процесс)

1.  Менеджер инициирует просмотр аналитики по мероприятиям.
2.  Система загружает из базы данных список мероприятий, по которым есть данные о продажах.
3.  Система отображает список мероприятий менеджеру.
4.  Менеджер выбирает мероприятие.
5.  Система загружает из базы данных сведения о проданных билетах и абонементах и занятых местах.
6.  Система рассчитывает показатели мероприятия: выручку, количество продаж, заполняемость стадиона и распределение мест по статусам.
7.  Система формирует отчет по мероприятию и отображает его менеджеру.
8.  Система передает агрегированные данные о продажах и занятых местах в систему анализа прибыльности мероприятия.
9.  Менеджер сохраняет (выгружает) отчет.
10. Система подтверждает успешное формирование аналитики.

Расширения (или альтернативные потоки)

*a. Каждый раз при попытке менеджера закрыть просмотр аналитики выполняются следующие действия.
```
  1.  Система возвращается к списку мероприятий.
  2.  Система сбрасывает несохраненный отчет.
```

*б. При каждом выходе системы из строя.
```
Для восстановления корректной работы необходимо повторно сформировать отчет.

  1.  Менеджер повторно входит в систему.
  2.  Система предлагает повторить формирование аналитики.
  3.  Менеджер подтверждает повторное формирование.
  4.  Система заново рассчитывает показатели мероприятия.
```

2а. В базе данных нет мероприятий с данными о продажах.
```
  1.  Система сообщает менеджеру об отсутствии данных о продажах.
  2.  Система предлагает выбрать другое мероприятие или вернуться позже.
  3.  Менеджер завершает просмотр аналитики.
```

5а. Ошибка загрузки данных о продажах из базы данных.
```
  1.  Система сообщает менеджеру о невозможности загрузить данные.
  2.  Менеджер повторяет попытку загрузки.
    2а.  Повторная загрузка завершилась неудачей.
      1. Система отменяет формирование отчета.
      2. Менеджер обращается к администратору системы.
```

6а. Обнаружены неполные данные о продажах.
```
  1.  Система уведомляет менеджера о некорректности данных.
  2.  Система регистрирует информацию об ошибке.
  3.  Система помечает отчет как предварительный.
  4.  Менеджер принимает отчет и сообщает об ошибке администратору.
```

7а. Система анализа прибыльности мероприятия недоступна.
```
  1.  Система сохраняет данные о продажах для отложенной передачи.
  2.  Система уведомляет менеджера о недоступности внешней системы.
  3.  При восстановлении связи система повторяет передачу данных.
```

9а. Ошибка сохранения отчета в базе данных.
```
  1.  Система уведомляет менеджера об ошибке сохранения.
  2.  Система предлагает повторить операцию.
    2а.  Повторное сохранение завершилось успешно.
      1. Система сохраняет отчет.
      2. Система подтверждает завершение операции.
    2б.  Повторное сохранение завершилось неудачей.
      1. Система сохраняет информацию об ошибке.
      2. Менеджер обращается к администратору системы.
```

Специальные требования.

- Интерфейс должен поддерживать визуальное отображение аналитики в виде таблиц и диаграмм.
- Система должна формировать отчет не более чем за 5 секунд в 95% случаев.
- Данные о продажах должны быть актуальны на момент формирования отчета.
- Необходимо обеспечить сохранение сформированного отчета после сбоя.
- Интерфейс должен поддерживать локализацию на различные языки.
- Доступ к аналитике должен быть разграничен по ролям пользователей.
- Должна быть возможность выгрузки отчета в файл.

Список технологий и типов данных.

2а. Данные о мероприятиях хранятся в базе данных.

5а. Данные о проданных билетах и абонементах загружаются из базы данных.

6а. Идентификатор мероприятия выбирается из списка.

6б. Показатели мероприятия рассчитываются на основе данных о продажах и схемы стадиона.

8а. Данные передаются в систему анализа прибыльности мероприятия по внешнему интерфейсу в структурированном формате.

9а. Отчет сохраняется в базе данных, а факт выгрузки фиксируется в журнале аудита.

Частота использования. После каждого мероприятия, несколько раз в месяц.

- Нужно ли отправлять отчет автоматически после завершения мероприятия?
